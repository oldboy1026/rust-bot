其余 13 个账号本轮均只有一张游戏票据、没有 steam_auth_lost；各有 2 个含性能事件的成功 HTTP 批次。四个不稳定账号的 worker 多次重启，世界/性能批次等不到原发送窗口，性能事件没有成功送出。这是认证重建造成的具体后果，不说明把所有上传窗口缩短就能解决公共人数。

27 次失效事件均先于本系统记录的同指纹游戏票据主动清理。服务器 EndSession 比对应失效回调晚 42–414 毫秒，控制端进入游戏票据清理晚 101–486 毫秒，所有清理原因都是 steam_auth_lost。没有发现这 27 张当前关联票据在失败之前被本系统 cancel_requested 的记录。时序只约束已记录的本系统动作，不证明外部取消者的身份，也不能保证所有服务器回调都属于当前尝试。

更强的证据是尾号 13895 的两次：Steam 客户端库也收到对应游戏票据 CRC 的 AuthTicketCanceled（controller 第 4595、5318 行），发生在控制端请求取消之前。它们证明至少这两张匹配票据确实失效，不能全部解释成插件误认旧回调。

同时存在 9 组相隔约 10 秒的连续失败，第二次已是不同票据指纹。例如尾号 04372 在 13:43:30/40、13:53:30/40、14:03:30/41；尾号 13895 在 13:45:50/13:46:00 和 13:55:50/13:56:00。新票据到失败的本地时间差从 1.717 秒到 305.191 秒不等，无法得出统一“票据五分钟到期”的结论。旧会话通知延迟可能放大短时间重建，但当前证据不能断言每个第二次回调都来自旧票据。

## 公共人数下降不是十三个稳定账号同时掉线

本轮控制端记录 436 个上传请求、433 个 HTTP 响应，响应全为 200；其余 3 个请求为两次因认证失败中断、一次尾号 65192 在 14:03:46 的网络超时。已记录的 433 个正常上传清理均收到确认，所有请求正文哈希核对一致，没有发现 HTTP 429 或明确 HTTP 认证拒绝。

十三个稳定账号在约 13:46:17–13:46:32 完成第一轮性能上传，在约 13:56:17–13:56:29 完成第二轮性能上传。第二轮上传发生在公共人数已经变成 2 之后，公共人数随后仍为 2。因此不能把整体下降简单归因于“上传停了”或“只要重传一次就会恢复”。

性能数据本身仍存在明显年龄差：第一轮约 13:41:43–13:41:57 采样，13:46 才发送；第二轮约 13:51:43–13:51:57 采样，13:56 才发送。HTTP 收到成功不等于平台按有效活跃玩家采纳。样本年龄、真实网络/EAC 状态、服务器端事件实际入库及上游聚合规则仍需要正常客户端对照；不能只凭空正文 200 认定流程闭环。

后台成功查询的缓存头均为 CF-Cache-Status: MISS，Last-Modified 距查询完成约 0.323–4.307 秒。它们不支持“网页未刷新/持续命中旧 CDN 缓存”作为主要解释；仍不能排除上游内部聚合或副本不同步。

## 源码的边界及已实施修改

AdminLogger 的 CreateBot 在源码中明确采用不创建真实 Connection、不加入 Net.sv.connections 的路径：创建 BasePlayer 实体，更新 SteamServer/PlatformService 名称与会话资料，然后手动提交服务器事件。控制端 FacepunchTelemetry 生成的是模拟客户端遥测。代码没有实现完整 Rust 网络握手、正常 ClientReady/传输保活与 EAC 客户端会话。通过 BeginAuthSession、显示实体和 HTTP 成功分别是可观测步骤，不是公共人数收录的确认。

因此，当前证据不能证明某个缺少的定时调用就是让 17 个都持续计数的开关，也不能直接把架构差异断定为 Facepunch 此次过滤的具体内部规则。要保证按正常玩家持续收录，必须用满足正常连接条件的客户端/平台支持路径验证，而不是仅让本地标记保持为真。

本次已改为 1.0.11（插件仍为 2.5.9）：

1. 只有当 Steam 通知的 CRC 匹配该游戏票据，且本地条目已经消失时，清理返回 already_invalidated，跳过额外取消 API；修复本轮两次“已失效却报取消失败”的清理误判。没有匹配证据的异常消失仍报错。
2. 认证失效后等待 30 秒再自动建立新租约，界面显示下次尝试时间。缓解已观察到的约 10 秒连续失败窗口；不忽略实际失败回调，也不保证这个等待覆盖全部迟到通知。
3. 记录每次遥测 AuthList 提交与 ACK 中的 CRC，直接检查游戏票据是否在遥测清理时被遗漏；日志不记录原票据或 GC 令牌。
4. 增加 CONTROLLER_TELEMETRY=off 隔离模式：暂停控制端客户端遥测，保留游戏认证、插件及后台采集，用于检验固定四个账号的取消是否依赖此流程。

## 下一步只做能区分原因的实验

第一组：新版本先在暂停客户端遥测模式下运行至少 15 分钟，观察原四个账号是否仍出现取消。该组用于判断取消依赖条件，不用于证明公共人数应该增加。执行方法见发行包 docs/POPULATION-DIAGNOSTICS.md。

第二组：选一个稳定账号和一个不稳定账号，分别使用正常 Rust 客户端连接同一服务器作对照；先停止它们的受管分配，避免同号并发会话。观察正常客户端是否被持续计数、是否同样出现取消，并与同时间段服务器日志对应。条件允许时保持正常客户端超过 20 分钟。

如果正常客户端稳定而受管路径不稳定，重点定位缺少的连接生命周期与当前 AuthList 流程；如果同一账号在正常客户端也失效，排查账号授权、其他登录/持票程序及 Steam 连接。暂停客户端遥测后仍失效，则它不是取消发生的必要条件；如果只在开启时复现，结合新增列表 CRC 再定位哪个动作改变了游戏票据状态。

本次没有声称实现“17 个账号全部持续被公共计数”。已修复的是能从日志和源码确认的清理误报，并增加有边界的重连缓解；平台最终为什么只保留总数 2，仍缺正常客户端/上游证据。缩短上传周期或隐藏失败不能代替这一验证。
