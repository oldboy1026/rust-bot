# Facepunch 1.0.4：性能首发与详细日志修复

2026-10-31。原项目已升级为 1.0.4，生产地址仍为 `https://gw.facepunch.com/analytics/rust/client`。

## 排查结论

用户反馈两条角色状态：input_events 均成功 5 批、HTTP 200，gameplay_events 尚无尝试。1.0.3 首次性能采样被安排在启动 600000 毫秒后，而不是输入批次的 60000 毫秒；约 5 次输入成功仍处于等待阶段，这份状态本身不能证明运行超过 10 分钟后也不发送。源码另确认：输入失败会 break 跳过同轮性能事件；性能事件在请求前即推进下次生成时间，失败批次又没有保留，可能丢失到下一轮采样。

## 修改后的行为

首轮约 1 分钟生成并发送输入和一条模拟性能事件，其后性能保持每 10 分钟生成，游戏事件表每 5 分钟检查，没有新事件不发空包。两表各保留最新一个待发批次，分别退避重试，输入错误不再跳过性能；HTTP 429 对同接口的两表共同遵守 Retry-After，队列保留。首轮后状态按表显示下次生成/发送时间、待发事件数；任一表失败时显示部分失败。

每个账号在 data/logs/facepunch/<账号>-<短标识>/events.jsonl 写入 UTF-8 JSON Lines。记录任务生命周期、生成/替换、票据申请确认、实际 URL 和请求头、完整 JSON 正文、gzip 前后大小与哈希、响应头和正文、耗时、底层网络错误、重试和票据清理。requestId 可关联整次操作。认证票据、密钥和 Cookie 自动遮盖；响应正文默认上限 256 KiB。每文件约 16 MiB 轮换，保留四份历史；日志错误通过状态显示，不阻断上传。

## 验证

36 项测试通过，28 个 JavaScript 文件语法检查通过。新测试验证首分钟性能及后续 10 分钟节奏、输入失败不抑制性能、失败性能一分钟后保留原事件重试、429 等待、日志正文/响应/关联编号/清理、凭据遮盖、响应截断、底层 ENOTFOUND 原因、文件轮换和磁盘写入错误。隔离空数据启动验证 health=200、状态工具退出码=0、shutdown=202，未加载真实账号。完整源码哈希及命令记录在 Facepunch后端实现验证-1.0.4.json。

新版性能请求的真实 Facepunch 响应需用户在公网测试机部署后查看；本次没有将本地接收测试冒充真实服务成功。用户提供的旧版输入 HTTP 200 是反馈证据，本次未独立采集远端响应。

## 升级与查看

先从管理页面正常停止旧控制端，将新包同名文件覆盖到原项目，保留 data 目录和自行修改的启动/代理配置，再启动。插件本次没有修改。首轮约 1 分钟后打开 facepunch-status.cmd，查看两类 HTTP 结果及每账号详细日志的实际文件路径。具体记录字段与轮换规则见 docs/FACEPUNCH-TEST.md。
