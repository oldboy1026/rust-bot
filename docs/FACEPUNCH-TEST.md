# Facepunch 自动上传：Windows 测试步骤

1.0.4 增加首轮性能上传、独立重试和按账号保存的详细日志。目标固定为 `https://gw.facepunch.com/analytics/rust/client`，不向游戏服务器地址发送这类 HTTP 请求。用户提供的 1.0.3 状态已显示输入批次收到 HTTP 200；新版性能批次的真实响应仍需部署后确认。

## 在测试服务器启动

1. 安装 Node.js 22 或更新版本，将新包解压到新的目录。首次双击 `start-network.cmd` 会按锁文件安装依赖，并监听 3220。若控制端和插件都在同一台 Windows 服务器，也可以双击 `start.cmd` 并使用回环地址。
2. 按项目原有流程打开管理页面、添加服务器并安装包内 `plugin/AdminLogger.cs`，用该服务器生成的配对配置连接控制端。已有同版本插件不需要为本次遥测功能修改。
3. 登录一个测试 Steam 账号，创建一条服务器分配。服务器设置中的游戏公网 IP、游戏端口必须正确；插件只报 `0.0.0.0` 时手动填写。角色名单核对成功后自动启动上传任务。
4. 在控制端目录双击 `facepunch-status.cmd`。首轮约 1 分钟后分别发送输入与模拟性能事件；两类结果都应出现 HTTP 响应。之后输入每分钟发送，性能每 10 分钟生成，游戏事件表每 5 分钟检查；没有新事件的检查不发空包。状态工具显示任务运行时长、每类的下次生成及发送/重试时间。
5. 停止该分配，再查看状态。上传任务应停止；现有流程会先结束遥测票据，再移除插件实体并取消入服票据。重新启动分配会生成新的客户端会话标识。

压缩包不含本机账号、数据目录、管理密钥、配对密钥或依赖目录；测试机需要重新登录及配置。不要复制另一台机器的 Windows DPAPI 账号库。完整部署说明见 [PUBLIC-DEPLOY.md](../PUBLIC-DEPLOY.md)。

在原测试机从 1.0.3 升级时：先通过管理页面正常停止控制端，用新包同名文件覆盖原项目，保留原来的 `data` 目录，再重新启动。原数据仍由同一 Windows 用户解密使用，不需要为本次后端更新重新安装插件。新包的生产请求仍直接发送到 Facepunch；自动测试接收端只存在于测试代码中。

## 为什么旧版只有 input_events

1.0.3 的首次性能事件要等 10 分钟，前 5 次左右的输入成功并不足以判断性能发送失败。旧代码还存在两个影响排查及重试的问题：输入失败会退出同轮循环，跳过已生成的性能批次；性能批次失败后没有保留，可能要再等下一次生成。1.0.4 在首轮生成一条模拟性能事件，两类上传分别保留最新待发批次并独立退避重试。遇到同一接口返回 HTTP 429 时，两类都遵守 Retry-After 暂停，性能批次保留到恢复后发送。

## 查看请求、响应和日志文件

默认目录是项目内 `data\logs\facepunch\<账号名>-<短标识>\events.jsonl`。若设置了 `CONTROLLER_DATA_DIR`，日志位于该数据目录内的 `logs\facepunch`。每个账号有独立目录，文件跨服务重启追加；`facepunch-status.cmd` 会打印当前账号的准确日志路径和最近请求编号。

文件为 UTF-8 JSON Lines，每行是一条完整 JSON 记录，可用文本编辑器查看。根据同一个 `requestId` 将申请票据、发送、响应和清理记录关联起来；根据 `accountId`、`displayName`、`assignmentId`、`steamId` 和 `sessionId` 区分账号、角色及不同运行会话。时间统一使用 UTC，`10:43Z` 对应北京时间 `18:43`。

| event | 内容 |
|---|---|
| worker_started / worker_stopped | 任务开始与结束、周期、模拟会话、累计成功及待发情况 |
| batch_generated / batch_replaced | 生成批次、事件 GUID、准备发送时间，以及被更新事件替换的旧批次 |
| ticket_requested / ticket_ready | 专用票据申请开始与 Steam 确认结果 |
| http_request | 实际 URL、POST 方法、请求头、完整 JSON 正文、gzip 前后字节数、JSON 与 gzip SHA256 |
| http_response | 实际 HTTP 状态与状态文本、响应头、响应正文、耗时、正文截断或读取错误标志 |
| ticket_cleanup | 本张票据清理确认、是否已收到 HTTP 成功、全程耗时 |
| attempt_failed / attempt_aborted | 失败或停止时中止、所处阶段、HTTP 码、错误及底层网络原因、连续失败次数、下次重试时间 |
| table_idle / waiting_context / worker_error | 等待性能采样、缺少角色或服务器地址、生成错误及其下次检查时间 |

请求头中的 `STEAM_TOKEN`、`X-API-KEY` 以及 Cookie 等凭据自动遮盖；正文中的模拟输入和性能值保留。响应正文默认最多记录解压后的 256 KiB，超过时 `truncated=true`；空响应显示 `body=""`。收到 HTTP 状态后，即使诊断正文读取有错误，也会记录 `readError`，不会把已知的成功响应误报为没有响应。

每个账号当前文件约 16 MiB 后轮换，保留 `events.1.jsonl` 至 `events.4.jsonl` 四份历史，`.1` 是最近的一份。旧历史超出数量时被替换。日志写入失败会通过状态工具的“日志错误”显示，不阻止正常上传。可反馈相关账号文件中的 request/response/failed/cleanup 记录；这些记录的时间和请求编号可用于后续分析。

## 如何判断结果

| 显示 | 含义与下一步 |
|---|---|
| 已启动，等待上传周期 | 任务已经启动，尚未到发送时间 |
| 部分上传失败 | 两类上传中存在失败；分别查看各类结果及其日志，不能仅凭另一类 HTTP 200 判定全部成功 |
| 等待服务器与角色信息 | 插件 hello 或角色 reconcile 尚未满足启动条件；检查服务器连接与分配状态 |
| 等待有效的游戏地址或角色信息 | 已有任务，但游戏地址缺失、插件断开或名单中没有该角色 |
| Steam 暂无可用的连接令牌 | 未取得用于创建这张票据的 GC token；会延迟重试 |
| HTTP 2xx / 成功批数增加 | Facepunch 返回 HTTP 成功；不等价于数据已写入统计、账号保持在线或公共人数变化 |
| HTTP 401/403 | Facepunch 拒绝认证或权限；需要进一步核对专用票据、identity 和服务端规则，不能当作成功 |
| HTTP 400/422 | 正文或协议可能不被接受；首先核对模拟输入中未恢复的三个整数和事件字段 |
| HTTP 429 | 上游限流；遵守 Retry-After 并延迟发送，不立即重复请求 |
| 网络失败或超时 | 检查测试机能否通过 HTTPS 访问 gw.facepunch.com 以及 Steam 登录服务 |
| Steam 确认未收到 | 10 秒内未收到匹配票据 CRC 的确认；仍可能交由 Facepunch 校验，不代表已经通过认证 |
| 票据清理确认未收到 | 这张票据已从本地列表精确移除，但未在时限内得到 Steam 对更新列表的确认 |

状态工具显示脱敏摘要和文件路径。也可在同目录执行 `node scripts/facepunch-status.mjs`，复制其输出反馈。详细请求及响应在上述日志文件中；管理接口 `/api/state` 的每条分配的 `facepunch` 字段提供摘要，不包含完整正文。状态计数按本次任务计算，文件历史跨重启保留。

## 数据与票据分别是什么

`analytics` 是 Steam 申请 WebAPI 票据时的服务用途字符串。这里申请 Rust AppID 252490 的 Type 5 票据，并附带 `str:analytics` 和结尾零字节；现有入服使用 Type 2 票据，不能直接替代。每个账号使用自己的已登录 Steam 连接、连接令牌和签名所有权票据。上传头中的 `STEAM_TOKEN` 是本次专用票据的 Base64 编码；`analytics` 本身不是密钥。票据不保存在状态、磁盘或日志中。

`session_id` 是客户端这次运行的事件关联标识，本实现每个账号任务生成一个 32 位十六进制随机值，同一任务中的输入与性能事件共用它。`guid` 是每条事件各自的随机标识。`server_session_id` 是服务器会话标识，本试验版按插件连接生成模拟值，同一个服务器连接的多个账号共享；它不冒充 SteamID，也没有恢复官方值的完整来源。`server_index` 暂用模拟值 1。它们都不是认证凭据。

输入格式已观察为 `version="4"` 和 `inputs` 有符号整数数组，每四个一组。第一列是相对于 `input_base_ticks` 的 .NET ticks，1 tick 为 100 纳秒；后三列语义尚未恢复。本版每 100 毫秒生成一条模拟记录，后三列使用零值占位；不宣称它们已正确表示按键或鼠标。每批最多覆盖最近 60 秒，失败后不积压或重放旧输入。

性能数据沿用观察到的字段结构，用生成值填写帧率、帧时、内存、硬件等。服务器地址、地图、世界种子和大小取当前插件及服务器设置；客户端硬件标为 Simulated。`steam_id_hash` 根据对应账号计算，不复制其他账号数据。服务端可能根据正文语义拒绝这些模拟值，这是公网实测要验证的内容。

默认首轮在 60 秒生成并发送输入和性能事件；其后输入表 60 秒、游戏事件表检查 300 秒、性能生成 600 秒。游戏事件表没有新性能事件时不发送空批次。上传使用 gzip 压缩的 UTF-8 JSON 数组。每账号串行上传，每次用专用票据，结束后精确移除这张票据；两类各保留最新一个批次，失败后至少等待 60 秒，逐步延长到最多 15 分钟，不立即叠加请求。新采样替换较旧待发数据时写入 batch_replaced 日志；429 的 Retry-After 可以要求更长等待。

## 本地已验证范围

执行 `npm test` 与 `npm run check`。测试覆盖 Steam ACK 不携带 JobID、独立票据类型和 identity、与游戏票据并存、两账号隔离、gzip/请求头/目标 URL、首分钟性能、后续周期、失败保留与分表重试、429 等待、停止时中止请求、晚到票据清理、插件 hello/角色返回后的启动条件，以及日志正文、响应、凭据遮盖、截断、轮换和磁盘错误。

本地自动测试将请求转接至回环 HTTP 接收端，Steam 部分由测试连接模拟；生产代码仍直接向 Facepunch 发送。用户提供的旧版状态是实际输入批次 HTTP 200 的反馈，并非本机独立采集的新响应；新版性能批次需在测试机确认。没有在本机用真实 Rust/Oxide/Carbon 程序集重新编译插件。
