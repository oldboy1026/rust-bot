# 1.0.12 / 2.5.9 人数下降诊断

1.0.12 新增服务器“一键停止”和账号区“一键退出全部”，保留下述取证及隔离能力。正常客户端、Steam 与 Facepunch 的联合采集按 [研究交接计划](CLIENT-STEAM-FACEPUNCH-RESEARCH.md) 执行。采样中点击停止或退出会主动结束会话，应记录为手动操作，不与自然认证失效混合分析。

本版增加取证能力，修复一个认证失败原因被丢弃的缺陷。现有日志还不能解释 Facepunch 最终计数规则，本版也不能保证公共人数维持在指定数值。没有根据约十分钟的相关性修改票据或上传周期。

1.0.11 根据本次日志新增：Steam 状态通知已确认当前票据失效，且该条目已不在本地列表时，清理返回 `already_invalidated`，不会再次调用取消 API，也不再误报清理错误；没有匹配通知的异常消失仍报错。认证失效后的自动重建等待 30 秒，降低短时间反复重建的风险；这只是对已观察到约 10 秒连续失败窗口的缓解，不证明所有第二次回调都来自旧票据，也不保证 30 秒覆盖全部迟到通知。票据仍以失败处理，不会忽略新会话的失败来虚报在线。

`auth_list_submitted` 记录发送给 Steam 的票据列表 CRC，`auth_list_ack` 记录相应确认中的 CRC。与游戏票据 `issued` 的 `steamTicketCrc` 对照，检查遥测票据添加/清理时是否保留游戏票据。`cancel_api_call` 才表示实际进入库取消方法；`cancel_requested` 表示清理流程启动，可能因票据已失效而跳过 API。

## 暂停客户端遥测的隔离测试

用于单独验证反复取消是否依赖控制端的客户端遥测票据流程。正常停止当前控制端后，在项目目录的 PowerShell 运行：

```powershell
$env:CONTROLLER_TELEMETRY = 'off'
npm.cmd start
```

启动时会明确显示「客户端遥测已暂停」。Steam 登录、游戏票据、插件实体及插件服务器端事件沿用原有路径，后台人数诊断也继续运行；只有控制端的客户端遥测工作器不启动。测试重点是原来四个账号是否还收到取消，不是此模式下公共人数能否增加。建议覆盖至少 15 分钟以包含已观察到的重复周期。

恢复正常模式时停止程序，再在同一终端运行：

```powershell
Remove-Item Env:CONTROLLER_TELEMETRY -ErrorAction SilentlyContinue
npm.cmd start
```

如暂停后仍发生取消，说明控制端客户端遥测上传不是该取消发生的必要条件；如不再发生，则仍需结合票据列表和正常模式复测排除时间、环境和账号状态差异。该实验也不能代替正常 Rust 客户端的连接对照。

## 升级与采集

1. 正常停止控制端，保留原有 `data`，替换发行包内的程序文件。不要同时启动新旧控制端。
2. 替换 Rust 服务器上的 `AdminLogger.cs` 并重载，确认插件版本为 **2.5.9**。插件重载会清理现有实体和服务器认证会话；控制端随后按原有流程重建。旧插件仍兼容后端，但无法提供服务器端的新审计记录。
3. 在服务器卡片「设置」核对游戏公网 IPv4 和游戏端口；UDP 查询端口用于 A2S，优先读取插件上报的 `query_port`，如有 NAT 映射请填写外部查询端口。不要用 RCON 端口，也不会猜测游戏端口加一。控制端所在机器需要能访问此 UDP 端口。
4. 点击「开启人数诊断」，然后正常启动测试会话。持续运行至少 **30 分钟**，尽量让一次人数下降自然发生，中途不手动停止或重启会话。开启状态会保存，重启控制端后会以新采集编号继续记录。
5. 记录人数首次稳定、开始下降、手动操作的时间和时区。完成后点击「停止人数诊断」。关闭网页不会停止后台采集，停止后保留已有日志。

需要提供的文件：`data/logs/controller/`、`data/logs/population/`、`data/logs/facepunch/` 的完整目录（包括轮换文件），以及同一时间段的 Rust 服务器控制台 / Oxide 日志。只打包日志即可，不需要账号库、密码、登录令牌或 API 密钥。

如条件允许，另做一组单个正常 Rust 客户端连接的基准测试，记录相同的三路人数和时间。这有助于区分服务器整体查询/上报问题与受管实体路径差异。不要在同一个账号上同时运行测试会话和正常客户端。

## 新增证据

| 记录 | 位置 | 可以回答的问题 |
| --- | --- | --- |
| `assignment_auth_attempt` | controller | 每次注册的 `attemptId`、租约 `leaseId` 与票据指纹是否变化；同票据是否再次用于注册 |
| `ticket_operation` / `ticketKind=game` | controller | 何时申请或主动取消游戏票据，取消由停止、删除、认证丢失、插件断线、账号连接变化还是服务停止触发 |
| `ticket_operation` / `ticketKind=analytics` | controller | 每次上传专用票据的申请、列表确认和精确移除；通过 `requestId` 对应现有 HTTP 上传日志 |
| `steam_ticket_status` | controller | Steam 库实际收到的票据状态通知；以库提供的 CRC 对应已记录的票据种类、指纹和租约/上传编号 |
| `plugin_auth_diagnostic` | controller | 服务器调用 BeginAuthSession / EndSession 的时间、结果、操作来源及异步认证回调 |
| `[AUTH-AUDIT]` | 服务器控制台 | 与插件上报相同的操作信息，含毫秒级 UTC `observedAt`，便于对齐双方时钟 |
| `population_sample` | population | 每轮本地状态、A2S 与 Facepunch 人数，以及每账号最后性能采样和上传的年龄 |

指纹是票据 SHA-256 的前 24 个十六进制字符，不含票据正文。每张游戏票据可对应多个注册尝试，因此不能只用指纹代替尝试编号。插件传统控制台指令没有控制端编号时会创建本地尝试编号。

`AuthTicketAlreadyUsed` 统一保存为 `AuthTicketInvalidAlreadyUsed`，避免 Facepunch Steamworks 枚举与控制端命名差异导致原因丢失。

## 判读边界

- **初步受理、最终回调与公共计数分别观察。** 插件实体存在或 `HasSteamSession=true` 不能单独证明最终认证通过。控制端的认证数表示最后一次成功回调尚未被本地观察到的失败撤销，并非对 Steam/EAC 的独立实时核验。
- **回调关联有不确定性。** Steam 原生回调只有账号 ID，没有票据或尝试编号。`validate_callback` / `assignment_auth_lost` 记录 `current_attempt_unverified`，表示关联到当前本地尝试，无法排除属于旧票据的延迟回调。不会据此忽略认证失败。
- **服务器 EndSession 与客户端取消是两类操作。** `end_requested/end_returned` 表示服务器结束验证会话；`game/cancel_requested` 表示控制端主动调用取消。返回成功只证明库调用结果及本地票据列表符合预期，不能证明上游已全链路确认。遥测清理只移除它自己的条目；游戏租约仍使用现有库的同 App 全部自有票据取消方式。
- **没有本地取消记录不等于已找到外部来源。** 若失败回调先于本系统全部 end/cancel 记录，只能排除已记录的本地主动操作在时间上的先行关系，仍需检查其他客户端登录、Steam 连接、账号授权和上游行为，并核对时钟偏差。
- **Steam 状态通知也不标识取消者。** `steam_ticket_status` 只记录库实际发出的通知；`library_crc_match` 表示按库 CRC 关联到本连接最近的已知票据，并非新增密码学验证。库找不到活动条目时可能不会转发通知，没有这条记录不能证明 Steam 没有发生状态变化。
- **三路数据不是同一时刻的事务快照。** 每轮本地快照有 `sampledAt` 和 `reconciledAt`；A2S 有独立请求起止时间；Facepunch 有查询时间、上次成功时间、数据时间和缓存头。请求并行执行，Facepunch 也可能复用管理页正在进行的请求。先检查时间与缓存，再解释人数差异。
- **A2S 只用于对照。** 返回的 `players` 和 `bots` 分开记录，不推算“真实人数”。A2S 本身可能受插件改写，因此也不是独立的真实玩家证明。超时、未知地址、分片或不支持的响应都标为未知/错误，不转成零人。当前只支持公开 IPv4、普通 A2S_INFO 和挑战应答。
- **HTTP 成功只表示 HTTP 成功。** `lastPerformanceSampleAt` 是最新生成事件的时间；`lastPerformanceUploadedAt` 是包含性能事件的批次最后获得成功 HTTP 响应的时间；`lastUploadedPerformanceSampleAt` 是该批次实际性能事件里的时间。三者不能混用，也都不保证公共人数采纳了该账号。
- **聚合接口不提供逐账号纳入名单。** 无法直接说哪七个账号被计数。必要时以单账号/少量账号分组和正常客户端对照实验缩小范围。最终确认上游拒绝或计数规则可能仍需要 Facepunch/Steam 的服务端证据。

## 如何缩小根因

先按 `captureId` 找到公共人数变化前后两分钟的快照：若本地认证/实体先减少，沿 `assignmentId → leaseId → attemptId → ticketFingerprint` 追踪首个失败和主动清理顺序。若本地状态稳定而 A2S 改变，检查服务器查询与插件状态。若 A2S 和本地都稳定而只有 Facepunch 改变，检查请求的新旧缓存节点、源数据时间以及每账号性能样本年龄，再用正常客户端对照；这能把排查范围缩到上报/聚合路径，但不能单凭差值证明上游过滤的具体原因。

后台默认每 10 秒采集，各轮不重叠，最多并行查询四台服务器。未开启时不增加后台查询。日志自动轮换，population 默认单文件 16 MiB、四份备份；控制端日志和每账号 Facepunch 日志沿用原有轮换配置。
