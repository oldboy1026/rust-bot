# 回家后的研究交接：Rust 客户端、Steam、Facepunch 与人数下降

更新日期：2026-11-11。交接版本：控制端 1.0.12，插件 2.5.9。时间线均为北京时间，原始日志里的 `Z` 表示 UTC，换算北京时间加 8 小时。

## 研究目标

观察一个真实 Rust 客户端从启动、进入测试服务器、保持不操作，到退出和重连的全过程；同时观察 Steam 认证和 Facepunch 上报。与当前控制端对照，定位两个不同问题：

1. 固定账号为什么反复收到 `AuthTicketCanceled`，是谁先改变了游戏票据或会话状态。
2. 其余账号没有观察到认证失效、仍成功上传时，为什么 Facepunch 公共人数仍下降，当前实现与正常客户端具体差在哪里。

用户希望会话持续稳定、人数不再逐渐下降。不能以隐藏失效回调、保持本地布尔值或 HTTP 200 作为解决依据。最终人数由平台判定，本次发行没有实现或验证“17 个账号全部长期计入”。

## 已有证据：不要重新从零排查

来源是用户 2026-11-11 14:04 左右结束的 `logs.zip`。测试 17 个账号，开始时用户认为没有真实玩家，中途有一名真实玩家进入。后台获得 131 个快照，覆盖 13:42:44—14:04:18，约 21 分 33 秒；这批证据已经足以确认下面的现象，不需要为了凑足 30 分钟重复同一轮。

| 已确认事项 | 证据及边界 |
| --- | --- |
| 四个账号反复认证失效 | Steam ID 尾号 04372、13895、59974、31375，分别 8、6、7、6 次，共 27 次，均为 AuthTicketCanceled |
| 其他十三个账号未记录认证失效 | 每个本轮只有一张游戏票据、没有 steam_auth_lost，各有两轮含性能事件的成功上传；这表示最后成功回调未被观察到的失败撤销，不是独立实时 Steam/EAC 核验 |
| 本地清理发生在失败通知之后 | 27 次关联清理原因均为 steam_auth_lost；服务器 EndSession 晚 42—414 毫秒，控制端游戏票据 cancel_requested 晚 101—486 毫秒；不证明取消者的身份 |
| 至少两张当前游戏票据确实失效 | 尾号 13895 在 13:46:00.656 / 13:50:40.118 收到 Steam 客户端库对应游戏票据 CRC 的取消状态，CRC 分别为 1793201465 / 3331447637，均早于本地取消 |
| 有约十秒连续失败的模式 | 九组第二次失败已经对应新票据指纹；又约每十分钟重复。不能证明第二次全是旧回调，也不能推导固定票据有效期 |
| 公共人数确实下降 | 13:41:53 首次 7；13:49:38 一名真实玩家进入，随后出现 8；13:51:25 首次 2，13:52:00 后成功查询一直为 2，直到结束 |
| 下降时本地角色与 A2S 没有相应下降 | 多个快照仍是插件实体 17、A2S 19、Bots 0；这些都不能当作真人或平台认可人数证明 |
| 继续上传没有恢复人数 | 十三个稳定账号在约 13:56:17—29 再次完成性能上传，公共人数仍为 2；本轮记录的 433 个 HTTP 响应全为 200 |
| 性能采样与发送有明显年龄差 | 首轮约 13:41:43—57 生成，13:46:17—32 发送；第二轮也约相差四分半钟，是否影响平台采纳未知 |
| 不能给 7 或 2 逐个分配身份 | 分配启动前公共接口已经出现 1/2，接口仅返回总数，没有纳入账号名单。不能认定固定七个或最后固定一个机器人，更不能用 13−7 定位六个账号 |

缓存头与数据时间不支持“浏览器一直显示旧缓存”作为主要解释，但不能排除上游内部聚合差异。7 首次出现早于第一轮性能 HTTP 上传，也不能认定第一次性能上传导致了 7。

## 当前项目实现到哪里

- `src/steam/accounts.js`：Steam 登录、Guard、连接状态、自动重试、退出。
- `src/steam/game-auth.js`：Rust AppID 252490 的游戏认证票据、租约、指纹、取消；游戏票据清理目前通过库按 AppID 取消本连接自有票据，不能假设与每张遥测票据的精确移除是同一机制。
- `src/steam/webapi-ticket.js`：`analytics` 用途的专用票据，以及 ClientAuthList 提交/ACK 审计。与游戏服务器会话票据区分追踪。
- `src/steam/features.js`：记录库收到的票据状态，按 CRC 关联最近已知票据。
- `src/bindings.js`：分配、注册、异步认证事件、清理及自动重建。
- `src/facepunch/telemetry.js` / `simulated-data.js`：模拟客户端事件及 HTTP 上传；HTTP 2xx 后本地记为 accepted，没有逐账号被公共人数采纳的确认。
- `plugin/AdminLogger.cs`：服务器 BeginAuthSession/EndSession、异步认证回调、实体与事件。创建 BasePlayer，不创建正常客户端 Connection、不加入 Net.sv.connections；没有实现完整 Rust 客户端网络生命周期或 EAC 会话。
- 插件手动 `EventRecord.Submit()` 成功只证明本地调用返回；现有 FP-EVENT 是部分原生 Analytics.Azure 回调的副本，不能代表全部 HTTP 上报或平台入库确认。手动事件不经过那些回调，缺少 FP-EVENT 行也不能直接证明手动事件未提交。

当前输入有未解码列的零值占位，性能包含模板及模拟值，连接标识由本地生成。正常客户端与此实现的关联方式、字段来源及生命周期需要核对；不要把代码注释中关于公共计数的猜测当成官方规则。

## 已经修正与保留的诊断能力

1. 角色注册成功与 Steam 最终认证分开；以异步 OK/lost 记录状态。
2. 游戏租约、注册尝试及票据指纹独立记录；Steam 回调仅携带账号 ID，关联当前尝试标为 current_attempt_unverified，不伪称精确归属。
3. 1.0.11 起：CRC 匹配的 Steam 失效通知，加本地票据已消失，清理返回 already_invalidated，跳过重复取消；缺乏匹配证据仍报错。
4. 认证失效后至少等待 30 秒重建，缓解快速连续失败；不是失效根因已解决的证明。
5. ClientAuthList 提交、ACK 与所列票据 CRC；cancel_api_call 区分实际进入库取消与仅启动清理。
6. 后台人数诊断每 10 秒记录本地状态、A2S、Facepunch、采样/上传时间及缓存信息。
7. CONTROLLER_TELEMETRY=off 可暂停控制端客户端遥测，保留游戏认证、插件服务器事件及人数诊断。

## 回家后先准备

1. 解压源码，安装 Node.js 22 或更新版本，双击 start.cmd；首次会安装锁定依赖。用 open-dashboard.cmd 打开控制台。
2. 发行包不包含 data、账号库、登录令牌或抓包。Windows 的旧加密数据绑定原用户/系统，不能假定复制到另一台电脑就能解密；在家中电脑重新添加自己的账号与服务器并配对即可。
3. 配套插件仍为 2.5.9。已有该版本无需为前端按钮更新重载插件；重载会结束现有插件实体/认证会话，应安排在采样前。
4. 测试服务器使用同一游戏地址、端口、地图与 EAC/安全设置。填写正确的公网地址和 UDP 查询端口，开启人数诊断。新控制端地址必须能被异地 Rust 服务器访问。
5. 先让服务器卡片“一键停止”结束受管会话，再用账号区“一键退出全部”断开控制端的 Steam 登录。仅“一键停止”会保留 Steam 登录，不适合用来排除同号并发连接。
6. 选一个之前稳定账号、一个失败账号（建议尾号 13895）分别测试；每轮只使用一个，不让正常客户端和控制端同时持有同账号的测试会话。登录验证由账号持有人完成。
7. 确认实际客户端安装路径、可用的抓包工具与采集权限。只采集测试进程/目标相关流量。保存客户端、Steam、控制端版本以及两端时钟差；不要把无法取得明文的连接记成已解析。

## 正常 Rust 客户端的日志开关

先创建 C:\RustLogs 文件夹，在 Steam 的 Rust 属性 → 启动选项追加以下参数，保留原有启动参数：

```text
-logfile "C:\RustLogs\normal-client.log"
```

启动游戏，在主菜单按 F1，执行：

```text
analytics.log true
analytics.log
```

确认返回 True。此开关在此前原生客户端采样中用过；如当前版本没有此命令，执行 `find analytics` 并保存返回结果，按实际版本核对，不使用猜测开关。结束后执行 `analytics.log false`。

原生 analytics.log 可能只打印提交的事件，不保证包含全部请求头、HTTP 响应或所有 Steam 消息。普通 PCAP 中 HTTPS 和 Steam 加密连接不能直接还原正文；优先对照原生日志、控制端库审计及服务器认证回调，拿不到的字段明确标为未知。

## 服务器端的现有日志

在服务器管理员控制台或 RCON 执行（不是普通客户端 F1）：

```text
rne.help
```

如果 debug=False，执行一次 `rne.debug`，确认 Debug: True。它是切换开关，重复会关闭。测试开始和结束各保存一次：

```text
rne.authstats
rne.status
rne.serverinfo
```

authstats 是进程内累计计数，不是当前同时在线数。现有日志已经包含 [FP-EVENT]，说明 dumpFacepunchServerEvents 已开启。通常文件在服务器日志根目录的 AdminLogger/fp_events-YYYY-MM-DD.log，Oxide 通常为 oxide/logs/AdminLogger/；实际路径按运行环境日志目录确定。

保存完整服务器控制台，包括 [AUTH-AUDIT]、[STEAMAUTH]、Analytics: ... emitted、真实玩家连接/断开及网络/EAC 原生消息。FP-EVENT 副本本身不构成完整的服务器→Facepunch 网络记录。

## 需要同时观察的三条链路

| 链路 | 需要记录 | 要回答的问题 |
| --- | --- | --- |
| 正常客户端/控制端 ↔ Steam | 登录/断开及重连、当前 Rust 游戏状态、游戏票据与 analytics 票据的申请/清理时刻、ClientAuthList 序号和 CRC 集合、ACK、票据状态与已知验证对端 | 遥测添加或清理时是否把游戏票据漏出列表；取消是否先于本地动作；是否发生另一客户端登录或连接重置 |
| 客户端/插件 ↔ Rust 服务器 | 真正网络连接、加载完成、持续网络收发、BeginAuthSession 的初步结果与最终回调、EndSession、EAC 状态、角色/会话移除 | 身份通过与真正完成入服之间差哪些步骤；取消属于哪次尝试，是否可精确关联 |
| 客户端/服务器 ↔ Facepunch | 请求目标/方法、事件类型、事件时间与上传时间、session_id/server_session_id/server_index 等可关联标识、请求与响应、持续在线及退出事件；同期公共人数 | 正常客户端靠哪些实际行为维持会话，当前路径是否缺失、延迟或关联不一致 |

正常 Steam 桌面客户端安装目录下的 logs/connection_log.txt（若该版本存在）可补充 CM 连接与重连证据；它不保证记录每张票据的取消者或完整认证消息，不能替代票据审计。对正常客户端没有得到的 ClientAuthList 明文，不用控制端的日志冒充。

请求记录保留目标、时间、非敏感字段、正文结构及响应；遮盖 STEAM_TOKEN、X-API-KEY、Authorization、Cookie、原票据、GC token、密码与刷新令牌。票据关联使用 CRC、哈希指纹、租约与尝试 ID。不得把另一个账号的日志正文或票据重放来代替观测。

## 实验顺序与判定

### A：建立可解释的基线

关闭所有受管分配，确认没有意外真实玩家。记录公共人数、A2S 与角色名单，等待数值稳定，并保留全过程；不假定会立即归零或某个固定等待时间就会过期。开始前仍非零时记为背景计数，不能把它指定给某个账号。

### B：一个正常 Rust 客户端，静止保持

从主菜单开始采集 → 连接同一测试服务器 → 记录完成加载时间 → 不操作保持至少 30 分钟 → 正常退出并继续观察人数变化。保存客户端日志、相关 PCAP、服务器事件、Steam 可用日志及后台人数采样。

先用稳定账号，再单独用失败账号。保持 EAC/服务器设置一致，记录任何 AFK 踢出或第三方玩家干扰。30 分钟用于覆盖已有重复窗口，不代表平台固定超时。

### C：同账号的当前控制端路径

正常客户端退出后，单独登录控制端，启动同账号的分配，以相同条件覆盖人数下降/认证失效。每轮使用独立文件，记录正常客户端和控制端切换时间。比较首次入服、持续在线、最后有效上报和退出/取消四段。

如果正常客户端也失败，优先排查账号授权、其他登录、Steam 连接及服务器环境。如果正常客户端稳定而当前路径下降，检查连接生命周期、认证列表及事件关联的差异。发现差异后通过针对性复测确认它与故障有关；差异本身不等于因果关系。

### D：仅隔离控制端的客户端遥测

正常停止控制端，在项目 PowerShell 运行：

```powershell
$env:CONTROLLER_TELEMETRY = 'off'
npm.cmd start
```

确认启动信息显示客户端遥测已暂停，针对原失败账号覆盖至少 15 分钟。此轮判断 AuthTicketCanceled 是否仍发生，不把公共人数是否增加作为成功标准。

停止后恢复：

```powershell
Remove-Item Env:CONTROLLER_TELEMETRY -ErrorAction SilentlyContinue
npm.cmd start
```

关闭遥测仍失败，说明遥测不是该失败发生的必要条件；关闭后未复现也不能单轮认定因果，需要恢复后重复，并核对实际 AuthList CRC。

### E：主动停止的对照样本

自然故障采样结束后，单独记录一次“一键停止”和一次“一键退出全部”。对齐本地 server_stopped/account_logout、服务器 EndSession、游戏取消 API 与后续 Steam 回调。这样能识别主动结束正常产生的通知，避免把它混入无人操作的取消案例。

### F：验证账号历史因素

只有明确单账号隔离后仍有计数差异，才研究历史因素。比较同一账号在正常客户端连接前后、当前路径的表现，并等待每轮背景计数稳定。不能从总数长期为 1 推导同一账号、不能把正常连接后改善单独归因于“上传过历史数据”；会话残留、时间窗口和环境变化都需控制。

## AuthTicketCanceled 的具体追踪方法

1. 按 accountId / Steam ID 建立时间线，用 assignmentId → leaseId → attemptId → ticketFingerprint → 已知 CRC 对应游戏票据；analytics 以 requestId 对应。
2. 将 issued、auth_list_submitted、auth_list_ack、Steam 状态、服务器 begin/validate/end、cancel_requested、cancel_api_call 放到同一毫秒时间轴，核对时钟偏差。
3. 比较每次添加/移除遥测票据的 AuthList，游戏票据 CRC 是否仍在所提交的集合中，以及 ACK 能确认什么。列表提交、ACK、最终游戏认证是三个不同阶段。
4. 如果只有服务器按 Steam ID 返回取消，保留 current_attempt_unverified；若客户端库也收到同 CRC 状态，可更强地确认当前票据已失效，但仍不能据此识别取消者。
5. 核对控制端 Steam 连接、账号其他登录和 Rust 桌面客户端是否在同一时刻改变状态；随后判断本地取消是原因还是失败后的清理结果。
6. 只有“匹配状态通知 + 本地条目消失 + 时间不早于出票”的情况下，already_invalidated 才有依据。缺少 cancel_api_call 不等于已找到外部取消来源。
7. 服务器 EndAuthSession 是结束本端验证会话；客户端 CancelAuthTicket/库取消是撤销自有票据。analytics 专用票据清理也不能直接当作游戏票据取消。以实际记录区分。
