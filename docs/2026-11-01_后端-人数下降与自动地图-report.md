# 人数下降日志分析与后端自动地图更新

分析日期：2026-11-01。后端1.0.7，插件2.5.7。报告类型：运行日志取证与 .NET 接口核对，flavor=null。

## 已确认的结果

两份压缩快照原先的24个后端/插件源文件完全相同，后期11份日志均包含早期日志的完整字节前缀，因此这次人数变化不能归为两个压缩包使用了不同版本代码。后期885次请求中有883条响应，全部HTTP 200且正文0字节；另有2次任务中止。没有证据证明被HTTP限流、被封号或遭到上游HTTP拒绝。

实际发现两项问题：所有账号均缺少世界资源资料；其中两个账号反复重建任务并丢弃待发事件。但其余九个账号仍持续请求，故这些问题不足以单独解释公共人数为何最终只有1。接口只返回服务器总数，不能识别哪个账号被计入，也无法证明其余6个账号从未被计入。

已在用户指定的“成功5个”目录实现自动地图资料读取、同步、重试、旧地图失效处理和后端处理日志，并完成本地验证。1.0.7未部署到用户实际服务器，未证明公共人数已恢复到11。

范围见 [scope.md](counts-20261101/scope.md)，时间线见 [timeline.md](counts-20261101/timeline.md)。原始日志保留在本机工作材料中，不随发布包分发。

## 地图为何一直缺失，已如何修正

旧插件上报了地图名与保存创建时间，却没有上报 `required_props`，后端的11个账号全部出现 `waiting_world_metadata`。旧插件发送 `level_url`，后端只读取 `map_url`，地图地址也没有进入后续数据。保存创建时间并不等同于原生使用的 `World.Timestamp`。

本轮只读核对本机已有 `Assembly-CSharp.dll`：它带有CLR元数据，SHA256为 `71c50c6f0a48f67702cc2328e255e0000803919599c6fea6705cc22c3aa94601`。PE元数据和IL读取未执行游戏DLL。关键的 `World.<Spawn>d__97.MoveNext` 直接说明原版如何取得世界资源：从 `World.Serialization.world.prefabs` 取id，经 `StringPool.Get` 转成资源路径，以忽略大小写的集合去重，调用 `AssetBundleBackend.GetRequiredAssetScenesForPrefabs`，合并 `AssetScene-props.common` 与 `AssetScene-props.other` 的值，转小写并排序。`World.Timestamp` 来自 `World.Serialization.Timestamp`，不是存档创建时间秒数。参考程序集的相关类型依赖包括 `WorldSerialization`、`WorldData`、`StringPool`、`FileSystem` 和 `AssetBundleBackend`；未发现需要脱混淆才能读取这些成员的情况。

2.5.7依据这些已核实的接口自动读取，不调用资源场景加载方法。扫描只在游戏主线程进行，WebSocket后台连接使用缓存；成功缓存5分钟，失败30秒重试，换图会清除旧资料并重新取得。启动完成时强制刷新一次，后端随hello及后续reconcile收取资料。真实成功取得的空资源数组可以保留，读取失败则明确标记等待/不可用，不用空数组冒充成功，不将旧手工配置套到新地图。

管理页会显示“地图资料已自动同步”或自动重试状态。用户仅需一次更新服务端插件；正常运行和换图不需要cmd导入或手填地图数据。参考DLL不等于远端版本一致性证明；完整插件仍需由实际服务器加载确认。

## 后端处理日志在哪里

运行后自动产生 `data/logs/controller/events.jsonl`；若设置 `CONTROLLER_DATA_DIR`，则在该数据目录下。它记录服务运行、登录与会话状态、标准认证失败原因、实体消失、插件断线、地图同步以及公共人数查询结果。记录的关联字段可与 `data/logs/facepunch/` 每账号日志对应。

公共人数日志在管理页处于查询状态时写入：首次、人数/状态变化和每分钟样本。页面关闭期间没有额外采样。`checkedAt` 是查询时间，`sourceUpdatedAt`/`cacheAge` 反映接口返回的数据时间和缓存情况，不是人数变化的精确时刻。每份运行日志约4MiB轮换，保留当前文件和4个备份。原始票据、密码与配对命令不写入运行日志。
